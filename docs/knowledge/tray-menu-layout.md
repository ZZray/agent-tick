# 托盘设置与二级菜单

作者：Ray Zhang。2026-11-02，基线 `36379a3`（0.5.22）。

## 截断原因

用户截图中的六宫格属于 `view=menu`，不是面板左下角的 `.settings-pop`。匿名 Chrome 夹具复现：展开“显示与通知”后内容增长，窗口仍停在首次打开的高度，底部设置与退出按钮不可见。

`menuWin.fit` 原先在 `wantShow=false` 时直接返回。首开会清掉这个标记，所以后续 ResizeObserver 即使上报新尺寸，宿主也不会调整窗口。菜单页面同时缺少高度限制和滚动区域；只放开原生 resize，仍会在设置比屏幕更高时越界。

## 0.5.23 的纵向展开修复

首开负责显示、激活和启动外部点击监听。已显示菜单收到新尺寸时，只调整位置与大小，不重新激活、不重复启动监听。隐藏时取消待显示请求，隐藏后的尺寸回调不能重新弹出窗口。

窗口尺寸限制在光标所在显示器的工作区内，边缘预留 10 CSS px。页面保留 300 CSS px 宽度，标题和底栏不压缩，中间的六宫格与设置共同滚动。选择器和提示继续使用已有滚动关闭逻辑。

网页向宿主上报标题、自然内容和底栏高度之和。不能用已经受 `100vh` 限制的外壳高度上报，否则窗口被限制后，展开与收起会丢失目标尺寸。每帧合并尺寸测量，展开、渲染和重新打开均触发测量。

本次保留已有 220ms 菜单入场、300ms 宫格动画及减少动态分支，没有增加窗口高度动画。未采用固定大窗口：它既浪费收起后的空间，也不能解决短屏可用高度。

## 验证边界

Go 几何测试覆盖底部与顶部任务栏、短工作区、150% 缩放的负坐标显示器、窄工作区及展开后回缩。Node 测试覆盖自然高度、重复尺寸回调合并与重新打开。匿名 Chrome 使用宿主尺寸夹具检查实际页面布局；这不等于真实 WebView2 的窗口定位或跨显示器 DPI 验收。

本轮结果：Node 111/111、Go vet/test 和 Windows 候选构建通过。Chrome 53/53，覆盖深浅主题、350/420/800px 高度、滚动后修改设置、选择器、底栏键盘可达、减少动态和重开；无页面异常。独立 Codex/OCR 复审无高置信度缺陷。DeepSeek 截图审提出底栏和焦点框裁切，但截图与 DOM 几何不支持这两项：800px 窗口的底栏处于 y=762–800，350px 窗口焦点框距底部约 3px。

未覆盖真实多屏混合 DPI、触屏以及操作系统焦点竞争。本次不修改大屏、通知内容、设置保存协议或自动更新逻辑。

## 右侧二级菜单

用户随后明确，“显示与通知”应打开侧面的二级菜单，主菜单不应向下展开。这是交互结构调整；0.5.23 的滚动修复只解决了截断，并未实现此要求。

采用专用的 owned popup，复用 `menuWin` 和原有 `tray.state/act`。主菜单保留六宫格、单行“显示与通知”入口及底栏；设置在 `view=menu&submenu=1` 中显示。独立窗口让主菜单尺寸与位置保持不变，子菜单按工作区向右定位，空间不足时向左避让，过高时仅滚动子菜单。

没有采用单个大窗口扩展并裁切区域的方式：已有 picker 按当前窗口定位，该方式还需要协调透明空白区域、输入命中和浮层裁切。本次只需要一个固定用途的子菜单，不引入通用菜单框架。

父、子窗口作为一组处理失焦和外部点击。两者之间切换焦点不关闭；关闭主菜单时取消子菜单待显示请求并一起收起。悬停只显示，显式进入才请求焦点；返回操作先关闭子菜单并回到主入口。设置保存继续走原有入口，不更改通知、大屏或任务状态。

本节记录 0.5.24 的实现约束。最终前端 Node 115 项通过；原生冷创建、显式焦点进入和创建途中取消三组验收通过。浏览器交互与原生窗口的验证范围分别记录在下文。

### 首次创建的焦点限制

原生匿名夹具首次打开子菜单失败：主窗口已经显示，但子菜单未能保持可见。回源 `go-webview2@56598839c808`，`CreateWithOptions` 在构造返回前执行 `ShowWindow` 和 `SetFocus`，此时产品还未登记子 HWND 及 owner，主窗口会把失焦判为离开菜单。该版本虽声明 `WebViewOptions.Window`，构造路径却未使用此字段，不能据接口名称推断它支持已有隐藏 HWND。

浏览器夹具没有覆盖这个原生构造行为。修复与验收必须保留首次冷创建，不能通过预热子窗口绕过问题，也不能在 `opening` 期间忽略所有外部失焦。

后续诊断读到 `HRESULT=0x800401F0`（`CO_E_NOTINITIALIZED`）。依赖仅在包初始化线程初始化 COM，新增子窗口线程需要显式 STA 初始化并在同线程平衡释放。诊断使用临时模块副本与 modfile，没有修改产品依赖或全局模块缓存。

焦点事件追踪定位到子窗口的 `ShowWindow(SW_SHOW)`：即使 CBT 拒绝目标激活，父窗口仍收到 `WA_INACTIVE(lp=0)`。尝试在 `CREATESTRUCT` 中设置样式未生效；显示前真实读数仍为 `style=04cf0000`、`exstyle=00000100`、`enabled=1`、`owner=0`。该回调只承诺结构中的位置、尺寸与层次修改，不能假定样式字段会写回窗口。

随后尝试对实际 HWND 设置构造期属性并取消激活 veto，原生验证仍失败。最初的结束快照显示前台为 ChatGPT，无法区分外部切焦与菜单关闭后恢复。追加的受控验证先确认主菜单已取得前台，再捕获首个失焦：此时实际前台与 GUI 焦点均为“Tick 显示与通知”子窗口，确认构造夺焦，而不是外部操作。

### 最终构造方式

删除 CBT、临时禁用及构造期样式拦截。`third_party/go-webview2` 保留当前固定版本的完整源码、两份许可证和 Loader；原有 50 个文件中 49 个逐字节不变，唯一代码补丁给 `WindowOptions` 增加默认 false 的 `Hidden`，启用时跳过构造中的 `ShowWindow/UpdateWindow/SetFocus`。只对子菜单启用，待布局准备好后由 `fit` 显示。维护边界见该目录 `UPSTREAM.md`；没有升级依赖或修改模块缓存。

两个菜单启用库已有的 `AutoFocus`，让实际键盘焦点进入 WebView 控件；移除激活后又把焦点强制移回顶层 HWND 的调用。跨线程 `WA_INACTIVE` 的目标可能为空，此时只在实际前台为另一个已注册菜单 HWND 时视为内部切换，不放宽正常的外部失焦关闭逻辑。

### 隐藏窗口的首次测量

隐藏创建后的首轮验收中，父窗口保持前台且 WebView 已获键盘焦点，子窗口也已 ready，但仍不可见、等待尺寸上报。源码中尺寸测量完全依赖 `requestAnimationFrame`；隐藏窗口可能暂停帧回调，而原生窗口又必须等尺寸才能显示，两者互相等待。

`tickMenuOpen` 现在同步读取自然内容尺寸并上报，取消尚未执行的旧帧。普通内容变化和 ResizeObserver 继续按帧合并，不更改其他视图的调度。新增测试不执行任何动画帧，仍要求首次打开与重新打开正确上报；原生复验三组均通过。失败记录未捕获 rAF 入口，因此“隐藏帧暂停”是源码与修复前后行为共同支持的解释，并非逐事件日志直接证明。

### 最终原生验收

2026-11-02，Windows 匿名夹具直接使用产品 `menuWin` 和内嵌 HTML、临时 Store 与 WebView profile，不连接正式会话服务。三组分别冷创建：悬停模式保持父前台，显式进入模式让子 WebView 控件获焦，取消模式要求迟到创建不能显示。另覆盖 owner/enabled、父位置不变、右边缘左翻、返回父菜单、外部激活关闭两窗和迟到 fit 不重开。

三组先核对父窗口实际取得前台；不满足时跳过且不计通过。最终 3/3 通过，约 18 秒。原生显式进入调用宿主 `openSub(focus=true)` 并核对真实焦点控件，不冒充实际方向键输入；Right/Left/Enter/Esc 与 picker 的按键路由由匿名 Chrome 交互验收覆盖。真实多屏混合 DPI、触屏、长期运行和用户主观观感仍未覆盖。

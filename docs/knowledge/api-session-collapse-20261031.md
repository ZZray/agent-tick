## 已复现的问题

### 主条目展开会强制显示未展开的子清单

初始父条目未展开时，两个子条目均为 `aria-expanded=false`，清单高度为 0。点击父条目后，子条目仍没有 `.open`、仍标记为未展开，但清单实际高度分别变成 246px 和 230px；340px 窄窗下为 481px 和 413px。

运行 HTML 第 333、336 行的 `.s.open .s-items` 和 `.s.open .s-items .pad` 使用后代选择器，也匹配子会话中的清单。子条目的独立展开状态因此失效。工作区相同规则仍在。

最小修正是把主条目规则限制到自己的直属 `.s-items` 及其内容，保留子条目的独立状态。验收应覆盖父开/子关、父开/子开后关子、父关/子开，逐项对照按钮状态与实际可见高度。

### 旧受阻项把正在做的步骤挤出当前窗口

快照中，主会话有 26 条清单：16 done、1 blocked、2 doing、7 todo。旧 `i14` 是数组第 12 项，因 M1–M20 尚待用户验收而保留 blocked；新工作 `i20`、`i21` 是数组第 18、19 项 doing。

`itemsHtml()` 一次顺序查找 `doing || blocked`，先命中旧受阻项，最终只显示数组第 11–16 项，两个正在做的步骤都藏在“后面还有 10 项”中。标题摘要使用 `current()`，却正确指向新工作并显示“另有 1 项并行”，所以标题与展开内容不一致。运行 HTML 第 2922 行及工作区同一逻辑均已核对。

最小修正是先找 doing，没有 doing 再找 blocked，再找 todo。该会话的两项 doing 应同时出现在当前窗口，旧 blocked 在完整清单中仍然保留；不能通过改掉真实受阻状态来掩盖显示问题。

## 需要区分的行为

父条目自己的清单与子任务区域目前是兄弟节点。展开一个子条目后再收起父条目，父自身清单变为 0px，子区域仍约 298px，这能解释“整个大条目收不起来”的观感。但现有代码刻意让子任务独立显示，尚不能据此认定父折叠必须隐藏整个子组。若要采用“父折叠后连子任务一起隐藏”的交互，应明确作为行为调整，并保留子条目的展开状态以便恢复。

父子关联正确，两个 doing 有并行说明，旧 blocked 的备注明确要求保留。会话标题沿用早期任务名、子 agent 被复用于新工作会使名称与当前步骤不一致，这是登记内容问题，不是 UI 算错状态；本轮未替其他会话改名。

## 标题与当前任务不一致的评估

用户截图中，本线程 `s_bfafe2` 仍显示初始标题“了解 Tick 项目”，实际已经经历修复发布和动画调查。此处是任务目标变化后标题未跟进，不是清单状态算错。用户同时担心改名后找不到原任务，询问是否应新建。

已核对 0.5.14 对应提交 `3207698` 的 `store.go:733–865`、`store.go:872–964`、`mcp.go:306–336`、`web/index.html` 详情标题及编辑入口，并读取当前安装技能和运行协议。相同 agent + externalId 再登记会拿回原会话并保留旧名；HTTP PATCH 和详情页能改标题，常用 MCP 工具没有改名入口。技能要求同一对话追加清单，另有“完全无关可新开”的表述，后者不能绕过现有 externalId 去重契约。只改技能不足以补齐入口和旧名查找。

建议先复用原卡片，标题采用“稳定主题 · 当前目标”，例如“Tick · 展开与标题优化”。目标实质变化时更新标题；普通步骤、追问和验证进度继续使用已有当前步骤行。改名保留会话 ID、清单历史与对话关联，旧名需要稳定保存并参与搜索；仅写入有数量上限的动态事件不足以保证旧名可找。补 MCP 改名入口及技能约束时，应同步维护项目技能源、安装输出和工具说明。若将改名合并进清单工具，需要明确一次操作的校验与失败语义，避免清单已修改但改名失败。

完全换项目或出现独立交付目标时，另建任务更清楚，但“同一对话关联多个任务”需要调整当前去重语义，建议后续单独设计，不伪造 conversation_id 规避关联。独立只读复核支持上述范围和旧名检索边界。当前为建议，未修改产品代码、共享技能或目标会话标题；未进行新功能运行验收。

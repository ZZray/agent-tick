# 悬浮窗拖宽与宽度记忆

2026-10-31，基于 `3207698` 加 Kiro 展开动画和设置弹窗的隔离工作区。用户要求原生悬浮窗支持横向拖宽并记住。未改安装版，未发布。

## 普通宽度与临时形态

普通悬浮窗的宽度存入既有 `desktop.json` 的 `Width`，单位为 CSS 像素。旧配置缺少该值时继续使用 340px；普通范围为 320–720px，同时受当前屏幕工作区限制。工作区临时不足时夹取显示宽度，不能因此把用户较宽的偏好覆盖掉。

胶囊保持 300px，环形列表、贴边长条和标签按原有布局决定尺寸，不写入普通宽度。尤其要区分 `f.set.Compact` 的保存偏好与页面当前形态：从贴边收起状态展开时，页面会暂时显示完整面板，原单行偏好保持不变；这个完整面板仍应能拖宽。

只在普通原生面板两侧显示 6px 拖拽区域；左停靠时拖右边，右停靠时拖左边，上下停靠可拖任一侧。窗口高度仍由内容和已有 ResizeObserver→`tickFit` 链路决定。

## 指针与结束顺序

既有窗口拖动已记录 WebView2 在捕获指针期间 `screenX/Y` 不可靠。调宽同样由宿主读取 `GetCursorPos`，按本次起点的绝对差计算，避免偏移累加；DPI 换算在宿主完成。

页面串行等待 Start、Step 和 End。拖动时暂停任务 morph，松手、取消、丢失捕获或失焦会唤醒尚未执行的动画帧，等在途 Step 完成后再执行 End，最终宽度不会被旧回包覆盖。切换胶囊、贴边收起或隐藏时也主动结束页面手势。

宿主复用现有拖动互斥和 `isDragging`，防止自动收起抢走手势；固定起始的对边，以及内容换行前的上下锚边。End 在锚点仍有效时先落最终矩形，再一次保存宽度和最终 XY，并释放互斥。隐藏、页面重新就绪、切换紧凑模式和两分钟兜底都要释放本次手势，不能只依赖页面收到 pointerup。

独立复审发现，长条展开后 600ms 内的旧临时锚点会覆盖拖宽矩形。现在主动拖宽优先；清单预留视口动画仍在运行时，拖宽沿用其冻结的 `resUp`，不重新按当前窗口中心判断方向。Kiro 的 `reserve_windows.go` 未修改。

拖宽本身不加动画；接手时取消正在运行的盒子形态变形。边缘悬停只有 100ms 颜色变化，清单展开与通知签名动效保持原实现。

## 验证

Go 回归 54 项、Node 30 项（其中拖宽交互 9 项）、`go vet`、内联 JavaScript 语法和 diff 检查通过。宿主受控检查覆盖左右边固定、DPI 换算、工作区限宽、临时形态与偏好分离、最终保存、失败释放及两项锚点优先级。独立复审发现的锚点冲突已修正并复核关闭。

Windows 隔离主程序构建并启动成功。在不操作界面的测试中，预置 `Width=520`，连续两次启动都读取到 96 DPI 下原生窗口宽 520px。该结果证明配置加载到实际窗口的恢复链路；不代表拖动输入和手感已验收。收据在 `D:/WorkSpace/tick-width-evidence-20261031-01a18c50/width-restore-checks.json`。

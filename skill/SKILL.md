# Tick：清单、进度和通知

远端电脑上的 agent 可以通过宿主电脑的 HTTP MCP 网关使用同一份看板。已连接 MCP 时直接调用 `tick_*` 工具，不需要在远端安装或启动另一份 Tick；连接地址和令牌由用户配置，令牌不要写进任务、清单或通知。

Tick 是用户本机的任务看板和置顶小窗（{{BASE}}）。用户不翻对话，而是看 Tick 来了解每个 agent 做到哪一步、卡在哪、问了什么问题。Tick 上的状态就是用户看到的事实：你没登记，用户就以为你没在干活；你停了却没更新，用户就以为你还在跑；你问了问题却没走 Tick，用户就不知道有人在等他。

## 规则（必须遵守）

1. **多步任务必须用 Tick。** 2 步以上或预计超过 5 分钟的任务，开工前先登记，不能做完再补。
2. **一个对话只有一个会话。** 同一对话里来了新任务，用 `tick add`（或 `tick plan`）把新条目追加到原会话，不要再 `start`。原会话已经 `finish` 过也照样追加，它会自动回到进行中。
3. **不另开重复会话。** 同一对话换目标仍复用原 `session_id`，不要省略或伪造 `conversation_id` 来绕过去重。`tick start` 的输出如果列出了“还有 N 个会话没收尾”，只处理本对话自己开的；不用做的条目 `skip` 并写原因，不处理其他对话的任务。
4. **清单必须完整。** 从第一步写到验证、提交，整件事要做的每一步都列出来，每条是一个能检查的结果；不要只写“分析 / 实现 / 测试”几个大阶段。
5. **每完成一条马上更新。** 开始某条前标 `doing`，做完马上标 `done` 并写一句能核对的结果。不要攒到最后一起勾，也不要做完了忘记勾。
6. **问题必须走 Tick。** 需要用户决定、确认或动手时，用 `tick wait` 把问题写清楚；用户在 Tick 和对话里都能看到。不要只在回复里问。
7. **用户回答后立刻更新。** 拿到回答的第一个动作就是更新 Tick：把接下来要做的那条标成 `doing`（会话自动从“等你”回到“进行中”）；不再需要的条目 `skip` 并写原因，计划变了就重发清单。不能让会话一直停在“等你”。
8. **做完必须收尾。** 全部做完（或者用户说不用做了）就 `tick finish` 写总结。不要让做完的会话一直挂在“进行中”。
9. **结束回复前状态必须对。** 做完用 `tick finish`；需要用户回答用 `tick wait`；等待依赖用 blocked；暂时停下待续用 `tick_pause`（命令行 `tick pause`）并写后续条件。执行器确实仍在后台运行时保留 running，说明当前对象和可查询的执行证据。不能为结束回复把未完成工作标成成功，或制造没有具体问题的“等你”。
10. **标题跟随目标，保留主题。** 当前目标实质变化时，用 `tick_rename`（命令行 `tick rename`）更新为“稳定主题 · 当前目标”，例如“Tick · 展开与标题优化”。普通步骤、追问和验证进度不改名。标题尽量简短，不把清单塞进标题；旧名由 Tick 保留供搜索，清单、状态和对话关联不变。重新 `start` 不会改名。
11. **多流程清单必须分模块。** 涉及多个阶段或职责时，用 `# 模块名`、`# 父流程 / 子流程` 分段，让用户从大屏看清“大模块 → 子模块 → 当前步骤”。按实际工作单元划分，通常一至三层足够；简单短任务可不分组，不为每条步骤创建一个模块。模块名简短、稳定，步骤写清对象、动作和可检查的结果，避免只有“处理”“继续”“测试中”。
12. **业务模块不登记成子 Agent。** 一个完整目标对应任务会话；业务分类用模块/子模块；只有真实独立执行者才用 `parent_session_id` 登记子会话。不为展示层级或绕过条目上限创建虚假子 Agent。模块进度从底层条目派生，不再追加“模块汇总任务”重复计算。
13. **执行结束与验证结果分开。** 开始先确定验收单位。API 测试通常一方法一条目，同方法复测更新同一稳定条目 ID，多次 Run 的证据链接写入 evidence，不增加方法总数。done 只表示执行结束；通过、失败、未知、未验证用 result 显式记录，排除用 skipped 并说明原因，不算通过。普通任务没有验证结果时不要补造 passed。
14. **处理 Tick 返回的遗漏提醒。** 工具响应可能指出本会话长期未更新的 doing，或收尾后仍未结束的条目。先核对真实执行证据：仍在执行就确认 doing 并更新真实阶段；等待依赖写 blocked 和恢复条件；已结束则补 done 与结果；明确取消才 skipped 并写原因。不要为了消除提醒编进度或批量勾完，也不必把无需用户回答的提醒转发成“等你”。

## 怎么调用

有 `tick_*` MCP 工具就用工具（`tick_start`、`tick_rename`、`tick_item`、`tick_plan`、`tick_notify`、`tick_pause`、`tick_finish`、`tick_show`）。没有就用命令行：

```text
{{EXE}}
```

下文的 `tick` 都指这个程序。PowerShell 里写成 `& '{{EXE}}' …`。它是窗口程序，PowerShell 要拿输出必须接管道：`$sid = & '{{EXE}}' start … | Select-Object -First 1`；直接赋值拿到的是空值。

## 流程

### 1. 开工前登记

```text
tick start "标题" "第1步" "第2步" … --agent <你的名字：claude / codex / cursor / kiro …> --ext <对话ID，能拿到就带>
```

输出第一行是会话 ID（`s_` 开头），本对话后续一直用它；在给用户的第一条进度回复里写一次。MCP 用 `tick_start`，返回里也有 `session_id`。

### 2. 写完整清单

- 按执行顺序排，每条写一个能检查的结果（“接口返回 404 时页面显示提示”，而不是“处理错误”）。
- 验证单独成条（编译、测试、截图核对、复审），提交 / 推送也单独成条。
- 一般 5 到 30 条；条目多没关系，漏掉步骤才是问题。
- **跨多个模块时按模块分段**：清单里单独一项写 `# 模块名`，它后面的条目都归这个模块，直到下一个 `# …`；单独一个 `#` 回到不分模块。标题行不算条目、不占序号。Tick 会按模块显示各自的进度。

```text
tick start "导出功能" "# 后端" "加导出接口" "补接口测试" "# 前端" "加导出按钮" "截图核对" "#" "提交推送" --agent codex
```

MCP 的 `items` 数组写法相同：`["# 后端", "加导出接口", "补接口测试", "# 前端", "加导出按钮", "#", "提交推送"]`。

有多层流程时，用 ` / ` 分隔模块路径，例如 `# 后端 / 接口 / 鉴权`。父模块与子模块的名字保持简短、稳定；步骤仍按实际顺序逐条汇报。大屏会在模块出现实际执行进度时展开对应分支，尚未执行的子流程不会提前铺满画布。模块卡来自原清单，不需要另开 Tick 会话；独立子 agent 仍使用 `parent_session_id`。

分组应能回答“目前在做哪一段、下一段是什么”。使用无限画布汇报多模块任务时，开工前把已知范围按大模块、子模块列完整；未来步骤保持 todo，完成步骤及时收尾，画布据此聚焦当前分支并汇总模块与总进度。不要把文件名、工具调用或每条步骤分别当作模块，也不要为了大屏增加没有实际工作的层级。

例如 API 验收清单可以这样写，当前执行哪一项，就把该项标为 doing：

```json
[
  "# 首轮验证 / 数据处理 / 二维处理",
  "调用二维傅里叶变换，核对输出矩阵尺寸",
  "调用二维相位校正，核对参数与结果",
  "# 首轮验证 / 设备采集",
  "读取采集状态，核对连接与空闲标志",
  "# 首轮验证 / 平台控制",
  "读取平台版本，核对版本字段与部署记录"
]
```

用户应能读出“首轮验证 → 数据处理 → 二维处理 → 调用二维傅里叶变换，核对输出矩阵尺寸”。重复验证同一 API 时，默认保留原模块和条目 ID，复测阶段与证据写入 note、evidence；仅在实际调整计划时按已有 ID 移组并保留历史，不再新建同方法条目。

执行时，先把当前步骤标 `doing`，完成就标 `done`，再进入下一步骤；切换模块前核对旧的 doing，仍受依赖阻断的写 blocked 和恢复条件。只有确实并行执行的步骤才同时处于 `doing`。长步骤用 note 更新真实阶段与证据入口，不能只更新会话标题，也不编造百分比。追加工作时带上新的模块标题，重发清单时保留仍适用的分组和步骤文字，避免已有状态和耗时失去对应。模块标题不标状态，不占条目序号。

需要重命名条目或移动模块时，使用计划对象中的现有 `id`；没有 ID 的旧字符串计划仍按文字匹配。通过 HTTP/MCP 更新单项可指定稳定 ID，避免依赖移动后的序号。清单最多 1000 项；较大清单按模块分批追加，不拆成虚假子会话绕过限制。

计划变了：`tick plan <会话> …` 重发完整清单（文字相同的条目保留状态和耗时），或 `tick add <会话> …` 追加。

目标变了：`tick rename <会话> "稳定主题 · 当前目标"`。MCP 用 `tick_rename`，传 `session_id` 和 `title`；保留同一张卡片及历史，不随每条清单改名。

### 3. 逐条勾选

```text
tick doing <会话> <序号>
tick done <会话> <序号> --note "一句能核对的结果，比如：12 个测试通过 / 截图里按钮已对齐"
tick skip <会话> <序号> --note "为什么不做"
```

序号从 1 开始，按条目算（模块标题不算）。耗时由 Tick 记录。

验证项可用 `tick done <会话> <条目ID> --result failed --evidence "日志路径或Run链接" --note "错误摘要"`；MCP `tick_item` 可用 `item_id` 代替 `n`，result 取 passed / failed / unknown / unverified，evidence 写实际证据入口。可继续的其他项继续执行，只有依赖失败的分支标 blocked，不自动把整个任务或所有模块转成“等你”。

**长步骤**：一条预计超过 10 分钟（全量编译、长测试、大批量处理），开始时在 `doing` 的 note 里写预计多久和在做什么，比如 `tick doing <会话> 4 --note "全量测试，预计 40 分钟"`；跑完马上 `done`。Tick 30 分钟没收到更新会把会话标成“可能掉线了”，写了预计时长用户就知道你还在跑。

### 4. 需要用户时

```text
tick wait <会话> --note "写成一眼能答的问题：A 还是 B？"
tick blocked <会话> --note "卡在哪：缺权限 / 环境没装 / 依赖服务挂了"
```

waiting 和 blocked 都暂停受影响条目的执行计时，但含义不同：waiting 必须有用户能回答的具体问题；blocked 写未满足的依赖、影响的分支和恢复条件。缺测试数据、缺实现、待集中修复或一次失败，不自动构成用户问题。只有等待用户的会话计入“等你”。

暂时停止但目标尚未结束时，用 `tick pause <会话> --note "恢复条件"`。pause 暂停正在执行的步骤计时；会话总历时仍按墙钟计算。只补写结果、证据或备注不会恢复步骤执行，下次实际开工再标 doing。

**做完了、只想问接下来做什么**（要不要编译、提交、打包）：只发一次 `tick wait`，问题里先一句结论再给选项，例如 `--note "已修好，测试通过。接下来？A) 编主程序 B) 提交 C) 先不动"`。不要先 `finish` 再 `wait`，用户会同时收到“做完了”和“在等你”两条提醒。用户选完：要接着做就 `doing`，不用做了就 `finish`。

**用户回答后**，第一个动作就是更新 Tick：接着执行就 `tick doing <会话> <下一条>`；计划变了先 `tick plan` 再 doing。仍有用户问题才继续 waiting，等待依赖用 blocked，暂时停止用 pause，目标完成才 finish。不要让 Tick 的状态与实际工作脱节。

### 5. 收尾

```text
tick finish <会话> --summary "改了什么、验证结果、没覆盖的部分"
```

没做成加 `--failed`，总结里写原因和现场。

### 6. 派子 agent

把你的会话 ID 交给它，让它登记时加 `--parent <你的会话ID>`（MCP 用 `parent_session_id`），它的进度会显示在你的会话下面。

你是被派出去的子 agent 时：登记必须带父会话 ID；不要自己 `wait` 问用户，要问的问题写进返回给主 agent 的结果，由主 agent 去问；返回前 `tick finish` 自己的会话。子 agent 问完就退场而不收尾，会话会一直挂在“等你”，用户回答之后也不会消失。

主 agent 收尾前，核对本次派出的子任务：已经返回的子 agent 必须完成自己的 Tick 会话，取消的工作写明原因；确实仍在执行的保留真实状态并说明。不要把未验证的结果勾成完成，也不要通过归档冒充收尾。归档是用户管理历史的操作，不能替代 Agent 汇报状态。

状态更新和通知分开：每个验收项都实时记状态、结果和证据，不为减少通知而漏报进度；主动通知按用户当前选择的密度发送，优先需要处理的异常和阶段结果，不为每次记录另发一条通知。托盘闪烁与悬浮徽标可以独立关闭，不影响进度记录和右下角提醒卡。

## 注意

- 上下文丢了、忘了会话 ID：用相同的 `--agent` 和 `--ext` 再 `start` 一次会拿回原会话（已归档的也会自动放回列表），不会开新的。所以 `--ext` 能拿到就一定要带（对话 ID）。
- 用户可能在 Tick 里把会话归档或删掉。归档的：你接着报进度，它会自动回到列表。删掉的：Tick 会报“没有会话”，说明用户不想再看到它；只有接着做同一件事时才用同样的 `--agent` 和 `--ext` 重新 `start`，会建一个新会话。
- 不确定做到哪一步：`tick show <会话>`。
- 清单、备注、通知里不写密钥、令牌、密码。
- 退出码 2 表示 Tick 没连上：不影响主任务，在回复里提一句，不要反复重试。
- 完整协议：{{BASE}}/protocol
